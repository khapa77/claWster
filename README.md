# ARM Cluster: Odroid-MC1 x12 + Odroid-HC1 + Raspberry Pi 4

## Конфигурация железа

| Узел | CPU | RAM | Сеть | Роль |
|------|-----|-----|------|------|
| Odroid-MC1 x12 | Exynos5422 ×4 = 48 ядер | 2GB/узел | GbE | Compute workers |
| Odroid-HC1 | Exynos5422 | 2GB | GbE | Storage (SATA) |
| RPi4 4GB | Cortex-A72 | 4GB | GbE | Control plane |

**Итого:** ~48 ARM-ядер на compute, хранилище на HC1, управление на RPi4.

---

## Варианты коммерческой реализации

### 1. Hosting/SaaS → K3s + Longhorn

**Что это:** Запускаешь контейнеры клиентов на кластере, предоставляешь веб-приложения/API как сервис.

**Архитектура:**
```
RPi4          → k3s server (control plane)
MC1 nodes     → k3s agents (workers)
HC1           → NFS/iSCSI storage backend
```

**Стек:**
- **K3s** — lightweight Kubernetes, хорошо работает на ARM
- **Longhorn** — блочное хранилище с репликацией между нодами
- **MetalLB** — LoadBalancer для bare-metal
- **Traefik** — ingress (уже в K3s)

**Как работает:**
- K3s управляет контейнерами (деплой, перезапуск, балансировка)
- Каждый клиент = отдельный namespace + Traefik ingress

**Монетизация:** помесячная оплата за namespace, CPU/RAM лимиты, домен

**Сложность:** средняя. Основная боль — изоляция клиентов и мониторинг.

---

### 2. Data Processing → Spark/Ray + MinIO

**Что это:** Клиент загружает данные, ты их обрабатываешь на 48 ядрах, возвращаешь результат.

**Архитектура:**
```
RPi4          → Master (Spark/Ray coordinator)
MC1 nodes     → Workers (compute)
HC1           → HDFS datanode / MinIO (S3-совместимое хранилище)
```

**Стек:**
- **Apache Spark** или **Ray** — распределённые вычисления
- **MinIO** на HC1 — S3-совместимое хранилище
- **Apache Kafka** — очередь событий

**Как работает:**
- MinIO принимает данные (S3 API — совместим со всем)
- Spark/Ray распределяет задачи по MC1-нодам
- RPi4 координирует job queue

**Монетизация:** оплата за CPU-часы или за объём обработанных данных

**Сложность:** высокая. Нужно управление очередями задач, изоляция job'ов, SLA.

---

### 3. Продажа вычислений → Kubernetes + Billing API

**Что это:** Клиент покупает "кусок" кластера (CPU/RAM/storage) и делает с ним что хочет — как мини-облако.

**Архитектура:**
```
RPi4          → k3s server (control plane)
MC1 nodes     → k3s agents (workers)
HC1           → persistent storage
```

**Стек:**
- **Kubernetes** — управление ресурсами, ResourceQuota на namespace
- **Prometheus** — сбор метрик потребления
- **Billing API** — подсчёт и выставление счетов
- **Rancher / Portainer** — UI для клиентов

**Как работает:**
- Kubernetes выдаёт клиенту изолированный namespace с ResourceQuota
- Billing API считает фактическое потребление (Prometheus метрики → биллинг)
- Клиент деплоит сам через kubectl или UI

**Монетизация:** pay-as-you-go или фиксированные тарифы (S/M/L)

**Сложность:** самая высокая. Нужны: биллинг-система, портал клиента, API, поддержка.

## Сравнение вариантов

| | Hosting/SaaS | Data Processing | Продажа вычислений |
|---|---|---|---|
| Порог входа | низкий | высокий | очень высокий |
| Маржинальность | средняя | высокая | низкая (конкуренция с AWS) |
| Целевой клиент | стартапы, разработчики | аналитики, data teams | DevOps-команды |
| Конкуренция | средняя | низкая (ARM-ниша) | очень высокая |

## Узкие места

1. **1Gb коммутатор** — с 48+ нодами трафик внутри кластера может стать бутылочным горлышком. Нужно продумать разбивку на VLAN или агрегацию портов.

2. **Питание** — MC1 x12 это серьёзная нагрузка (~10-15A на 5V/12V). Нужен нормальный UPS и PDU.

3. **Хранилище** — HC1 один, если хочешь отказоустойчивость — нужно минимум 3 узла для Ceph/GlusterFS.

4. **Гетерогенность** — Exynos5422 (MC1/HC1) vs BCM2711 (RPi4). Разные архитектуры не проблема (всё ARM), но планировщик Kubernetes надо настраивать через `nodeSelector`/`taints`.

---

## Конкурентное преимущество

**ARM-ниша** — главный аргумент для позиционирования. Data processing на ARM дешевле по энергопотреблению — это аргумент для "зелёного" (green computing) позиционирования и снижения OPEX.
